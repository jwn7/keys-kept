# 보안 설계: 무엇을 막고, 무엇으로 막는가

위협 모델 한 줄 요약은 `docs/SPEC.md` §7. 이 문서는 요즘 실제로 일어나는 공격별로 이 앱의 대응과, 앞으로 넣을 "우리만의" 방어를 적는다.

## 원칙: 암호 알고리즘은 만들지 않고, 조합을 설계한다
- 새 암호 알고리즘(원시 함수)을 만드는 것은 독특함이 곧 약점이다. 공개 검증을 수년간 버틴 것만 쓴다: `libsodium`의 Argon2id, XChaCha20-Poly1305 (CLAUDE.md 규칙 1, 유지).
- 차별점은 그 위층에서 만든다: 검증된 부품을 **어떻게 조합해 무엇을 막는가**. 아래 "제안"은 전부 표준 부품의 조합이다.
- 주장은 확인할 수 있어야 한다. 막는다고 쓴 것은 테스트나 스크립트로 재현한다.

### CSP가 실제로 막는지 확인하는 법
```
pnpm --filter @vault/web build
pnpm --filter @vault/web preview        # 다른 터미널
node apps/web/scripts/csp-check.mjs
```
배포 빌드에서 앱을 한 바퀴 돌려 정책 위반이 없는지 보고, 끼어든 스크립트인 척 `fetch`·이미지·바깥 스크립트·`eval`을 시도해 전부 막히는지 본다. CI의 e2e 작업에서도 돌린다.
개발 서버(`pnpm dev`)에는 CSP가 없다(HMR이 인라인 스크립트를 쓴다).

## 제안: 우리만의 방어 (저장 형식이 바뀌므로 승인 후 진행)
한번 동기화되면 되돌리기 어려운 변경이라 따로 설계·테스트한다. 추천 순서대로.

1. **크기 감추기(패딩)**: 지금은 암호문 길이로 메모 길이를 알 수 있다. 암호화 전에 평문을 구간 크기로 채운다(Padmé 방식, 최대 약 12% 증가). 서버가 아는 것이 "개수와 시각"으로 줄어든다. 예전 버전도 읽을 수 있게 넣을 수 있다.
2. **되돌리기 공격 감지**: 악성 서버가 옛 암호문을 다시 내려보내거나 일부를 숨겨도 지금은 알기 어렵다. 기기마다 "내가 본 항목별 최신 버전" 요약을 암호화해 두고, 서버가 더 낮은 버전을 주면 경고한다.
3. **열쇠 확약(key commitment)**: XChaCha20-Poly1305는 한 암호문이 여러 열쇠로 풀리게 만들 수 있다. 악성 서버가 조작한 열쇠 기록으로 비밀번호 후보를 한 번에 여러 개씩 걸러내는 공격(partitioning oracle)의 여지를 없애려면, 감싼 열쇠에 열쇠의 해시(`crypto_generichash`)를 같이 두고 확인한다.
4. **가짜 금고(강요 대응)**: 다른 비밀번호를 넣으면 다른 메모 묶음이 열린다. 누가 강제로 열게 해도 진짜가 따로 있다는 것을 증명할 수 없게 한다. 메모 앱에서는 드문 기능이고 설명하기 쉽다. 설계가 가장 크다(항목 수로 들키지 않게 하려면 1번 패딩과 가짜 항목이 같이 필요).
5. **빌드 지문**: 실행 중인 앱 파일들의 해시를 설정에 보여주고, 같은 값을 공개 저장소의 릴리스에 올린다. 서버가 코드를 바꿔 내려보내면 지문이 달라진다. 서버가 지문 표시까지 속일 수 있으므로 완전한 해결은 아니고, 제3자가 감시할 수 있게 하는 장치다.

## 뜻 색인을 넣을 때 지켜야 할 것
임베딩 벡터에서 원문을 거의 복원할 수 있다(연구로 확인됨). 그래서 벡터는 메모와 똑같이 itemsKey로 암호화하고 `sync/`로만 내보낸다. 모델 파일은 받기 전에 크기와 출처를 알리고, 받은 뒤 해시를 확인한다. 추론 중에는 네트워크 요청이 없어야 한다(CSP가 이미 강제).
