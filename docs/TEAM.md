# 팀 공유

## 1판: 파일로 주고받기 (만들어져 있음)
서버가 없다. 프로젝트의 값을 **받는 사람의 공개키로 잠근 파일**로 만들어 건넨다. 파일이 메신저나 메일을 거쳐도 받는 사람만 연다. 비밀번호를 같이 쓰지 않는다.

### 쓰는 법
1. 각자 프로젝트 화면의 **팀원에게 보내기**에서 "공유 열쇠 만들기"를 한 번 누른다. 개인키는 금고의 "팀" 프로젝트에 키 항목으로 들어가고, 화면에 공개키(`age1…`)가 나온다.
2. 공개키를 팀원에게 알려 준다. 받은 쪽은 이름과 공개키를 "팀원 추가"에 넣는다.
3. 보낼 사람을 고르고 파일을 만든다. 표준 age 파일(`.env.age`)이 내려받아진다.
4. 받은 사람은 **.env 넣기 → 받은 파일 열기**로 자기 금고에 넣거나, 파일째로 쓴다:
   ```
   VAULT_ENV_IDENTITY_FILE=내개인키.txt  node packages/env/bin/vault-run.mjs --file .env.age -- npm run dev
   ```
   age만으로도 열린다: `age -d -i 내개인키.txt .env.age`

### 어떻게 잠그나
- 암호는 직접 만들지 않았다. age 포맷의 수신자 모드이고 `age-encryption` 라이브러리가 한다 (`packages/core/src/secrets/share.ts`).
- 열쇠는 양자내성 혼합형(ML-KEM + X25519)이다. 지금 가로챈 파일을 나중에 양자컴퓨터로 푸는 공격을 피하려는 것이다.
- 보내는 사람의 공개키도 받는 사람 목록에 넣는다(내가 만든 파일을 나도 열 수 있게).
- 개인키와 팀원 공개키는 금고의 키 항목이다. 다른 키와 똑같이 암호화되고 내 기기끼리 동기화된다.

### 알고 써야 할 한계
- **보낸 파일은 그 시점의 사본이다.** 내가 값을 바꿔도 팀원의 것은 안 바뀐다. 다시 보내야 한다.
- **회수할 수 없다.** 팀원이 떠나면 그 사람이 받은 키는 전부 다시 발급해야 한다. 사고 모드에서 프로젝트를 고르면 바꿀 목록이 나온다.
- **공개키가 진짜 그 사람 것인지는 이 앱이 모른다.** 메신저로 받은 공개키는 중간에서 바뀌었을 수 있다. 화면의 지문(16진수 네 묶음)을 전화나 대면으로 맞춰 본다.
- 누가 언제 무엇을 받았는지의 기록이 없다.
- 외부 보안 검토를 받지 않았다.

## 2판: 같이 쓰는 프로젝트 (설계만, 아직 안 만듦)
여러 사람이 한 프로젝트를 같이 고치고 바뀐 것이 자동으로 퍼지는 방식. 서버(또는 공유 폴더)가 필요하다.

- 프로젝트마다 열쇠 하나. 그 열쇠를 멤버 각자의 공개키로 감싸 저장소에 둔다. 저장소는 여전히 내용을 못 본다.
- 정해야 할 것
  - 저장 위치: 공유 Drive 폴더, Supabase, 또는 깃 저장소 안의 암호문.
  - 멤버를 뺄 때: 프로젝트 열쇠를 바꾸고 남은 멤버에게 다시 감싸 준다. 그래도 떠난 사람이 예전에 본 값은 그대로이므로 키 자체를 재발급해야 한다.
  - 누가 멤버를 넣고 뺄 수 있는가(관리자 서명), 초대를 어떻게 확인하는가.
  - 바뀐 기록: 누가 어떤 키를 언제 바꿨는지를 암호문 안에 남긴다.
  - 악성 저장소가 멤버 목록을 바꿔치기하는 공격(자기 공개키를 끼워 넣기)을 어떻게 막는가. 멤버 목록에 관리자 서명이 필요하다.
- 한번 넣으면 되돌리기 어렵다. 공격 테스트를 먼저 쓰고 승인받은 뒤 만든다.
